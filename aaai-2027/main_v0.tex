\begin{abstract}
\begin{notstarted}
When a long-context input is longer than the model's window, something must be removed. Benchmark harnesses usually cut out the middle of the prompt. We study this \emph{overflow policy} directly and treat retrieval as query-aware truncation: it re-renders the same prompt but keeps the chunks most similar to the question. On AA-LCR, MRCR v2 and LongBench-v2, served by one open-weight model at the same token budget, we compare it with naive truncation, structural and random controls, lexical retrieval and an oracle. The abstract will report how much of the accuracy lost to truncation it recovers, and how much of the oracle's gain.
\end{notstarted}
\end{abstract}

\section{Methodology}
A prompt holds fixed instructions, one or more source documents and a question. Its input budget $B$ is the context window minus the tokens reserved for the answer. We count tokens on the fully rendered request, with the served model's tokenizer and chat template, so $B$ bounds exactly what the model receives. A prompt that fits is sent unchanged. An \emph{overflow policy} decides what a longer prompt becomes. All policies run in one pipeline that is otherwise identical across conditions, and in every condition we report the instructions and the question reach the model intact: policies differ only in which source text they keep.

\subsection{Truncation Policies}
Truncation cuts the final message by token count. \emph{Middle truncation}, the LongBench protocol \review{cite LongBench}, keeps equal numbers of tokens from its start and end and silently drops the middle. \emph{Marked middle truncation} makes the same cut but inserts an omission marker, which tests whether knowing that text is missing helps the model. \emph{Head} keeps only the start of the context, followed by the question.

\subsection{Selection Policies}
Selection rebuilds the same prompt from a subset of its source text in three steps that every ranking shares, so two selection policies differ only in their ranking. \review{Terminology: the title says query-aware truncation; this section says selection, which also covers the two question-blind controls. Keep both terms?}

\paragraph{Chunking.} Each document is split into overlapping chunks, measured with the embedding model's tokenizer. Every chunk keeps its exact character offsets, so every kept span is verbatim source text. Unless stated otherwise, chunks are 7,500 tokens with 750 of overlap, our pipeline's default, on AA-LCR and LongBench-v2. On MRCR they are 3,500 with 350, chosen in early runs there; with 7,500-token chunks, dense exact match on MRCR falls from 55.0\% to 45.0\% ($-$10.0 points [$-$17.5, $-$2.5]).

\paragraph{Ranking.} A ranking orders all chunks of a prompt, with no top-$k$ cut. Three rankings use the question: BM25 ($k_1 = 1.2$, $b = 0.75$, on lower-cased words) \review{cite BM25}; dense, by cosine similarity between Qwen3-Embedding-0.6B embeddings of each chunk and of an instruction-prefixed query \review{cite Qwen3-Embedding}; and fusion, by reciprocal-rank fusion ($k = 60$) of the two \review{cite RRF}. The query is the question on AA-LCR and the question with its four choices on LongBench-v2. On MRCR it is the description of the requested item (its format, topic and style), because the prefix the answer must start with is random and the ordinal (``the second poem'') never appears in the conversation. The needle requests repeat this description almost word for word, which favours lexical matching. Two controls ignore the question. \emph{Position} orders chunks by their distance from the nearer end of their document, taking the documents in order at each distance, so heads and tails are kept first. \emph{Random} shuffles the chunks with a fixed seed per question. Position builds a prompt with the same structure as a retrieval prompt (documents in order, under their headers, with omission markers) without using the question, from the same chunks and with the same packing as BM25 and dense, so comparing it with them separates the effect of the prompt's structure from that of selection.

\paragraph{Packing and rendering.} Chunks are added in rank order for as long as the re-rendered prompt fits $B$. Kept spans are merged where they overlap or touch, put back in source order and rendered into the original prompt template, with an omission marker wherever text was dropped, as in order-preserving retrieval \review{cite OP-RAG, DOS RAG}. On AA-LCR, documents keep their original numbers, and a document with no kept span is left out. By default packing stops at the first chunk that does not fit, so selection sends fewer tokens than truncation at the same budget: under 1\% fewer at MRCR's 262K window, 3--6\% at 64K and 7--15\% at 32K. \emph{Fill} packing instead trims the best remaining chunk to the leftover budget.

\paragraph{The \recipe.} Our main method adds four steps to fusion, each a rung of an ablation ladder on MRCR and LongBench-v2 (see Experiments): 1,024-token chunks with 128 of overlap; each chunk widened by one neighbouring chunk on each side; fill packing; and a document floor, which offers the best chunk of every document before any document's second chunk.

\paragraph{Oracle.} MRCR marks which turns hold the answer, so we can build an oracle from the \recipe: chunks that overlap the target turn are offered first, then those overlapping the other needle turns, then the rest in the recipe's order. Only this order uses gold data; chunking, packing and rendering are unchanged. The oracle therefore shows what the same prompt format achieves when ranking never misses the answer.

\paragraph{Provenance and visibility.} Each answer records the character ranges its prompt kept, and truncated prompts can be rebuilt exactly. On MRCR we can therefore tell whether a prompt held the whole target turn and all needle turns, and split exact match into how often the target was visible and how often the model answered correctly when it was (Table~\ref{tab:visibility}). AA-LCR and LongBench-v2 do not release evidence locations, so this split is limited to MRCR.

\section{Experiments}
\paragraph{Setup.} We serve Qwen3.6-35B-A3B \review{cite Qwen3.6}, an open-weight mixture-of-experts model with a 262K-token window, with vLLM 0.19.1 \review{cite vLLM} on four NVIDIA L40S GPUs, and send it one request at a time. Decoding is greedy, with thinking disabled. AA-LCR uses its official prompt and MRCR v2 its released prompts. On LongBench-v2 a system prompt asks for a single letter, and decoding is constrained to A--D. The answer reserve is 4,096 tokens on AA-LCR and MRCR and 8 on LongBench-v2. Within a benchmark, every condition uses the same questions, prompt template, model and serving setup, and conditions are compared question by question. \review{Only one model family was run. Say so here, or only in Limitations?}

\paragraph{Conditions.} We ran the conditions in three stages. The first stage separates a prompt's structure from selection: marked middle truncation, head, position and random chunks (three seeds on AA-LCR, one elsewhere), next to middle truncation and dense retrieval, all at the main window. The second adds BM25 and fusion on all three benchmarks, and an ablation ladder on MRCR and LongBench-v2 only, which adds the \recipe's four steps to fusion one run at a time. No step's interval excludes zero on either benchmark. The last two rungs score the same, because the document floor has no effect on a single document. As planned, the final rung became the \recipe{}, fixed before any run of it on AA-LCR or at another window. \review{Per-step ladder numbers: an appendix table, or one sentence in Results?} On MRCR, a further dense run with the full question as its query scores 45.8\% against 55.0\% ($-$9.2 points [$-$15.0, $-$4.2]), which supports the request-description query. In the third stage, AA-LCR, the only multi-document benchmark, serves as the held-out check: no setting of the recipe was chosen on its scores, and the recipe runs on it once per window. Because the ladders could not test the document floor, we later also ran the recipe without it on AA-LCR. It scored 56\%, 63\% and 62\% at 32K, 64K and 80K against the recipe's 56\%, 58\% and 64\%, within the noise between serving nodes described below, so the recipe stayed as fixed.

\paragraph{Budgets.} The main window is 64K on AA-LCR and LongBench-v2, where every prompt overflows, and the model's full 262K on MRCR. Middle truncation, position, BM25 and the \recipe{} also run at 32K and 80K on AA-LCR, 32K, 64K and 128K on MRCR, and 32K and 128K on LongBench-v2, with the same answer reserve; on MRCR the oracle runs at every window. AA-LCR stops at 80K because every prompt fits 128K, while at 80K none fits and middle truncation keeps 74\%. Full context is the 262K run on AA-LCR and LongBench-v2, in which every prompt fits.

\paragraph{Grading.} MRCR and LongBench-v2 are scored deterministically. AA-LCR's prompt asks for no answer format, and with thinking disabled the model often explains or works through the problem in its answer; 4.9\% of answers reach the 4,096-token cap, and nearly all of these are graded incorrect. Full context never reaches the cap; middle truncation does on 5 to 8 of its 100 answers at each window, and the recipe on 3 to 7. We grade with the benchmark's own equality checker, GPT-5.6 Luna at medium reasoning effort with the official grader prompt. \review{Cite the AA-LCR methodology page for the checker model; the repository records no source for it.} It sees the question, the reference and the answer, and judges the value the answer finally commits to. To check it, the served model also graded every answer. Over the 23 AA-LCR runs the two graders disagree on 27 of 2,300 answers. We labelled all 27 by hand, mixed with 30 random agreements and without seeing either grade. Luna is right on 21 of the 27, and both graders are right on all 30 agreements, so we estimate Luna's accuracy at 99.7\% (95\% interval [88.3, 99.7]). Its six known errors, four lenient and two strict, fall in five runs and change no run's accuracy by more than one point.

\paragraph{Statistics.} Each condition runs once. We report paired differences from middle truncation at the same window, with 95\% percentile intervals from 10,000 bootstrap resamples. Questions that share a source are resampled together: the 30 document sets of AA-LCR and the 194 texts of LongBench-v2. MRCR has only four conversations, so we resample questions within each conversation, and its intervals hold for these four conversations only. Every comparison within a benchmark uses the same resamples. We call a difference clear when its interval excludes zero; the intervals are not corrected for the number of comparisons. For a reference that beats middle truncation, either full context or the MRCR oracle, we also report the share of its gain a policy recovers, $(s - s_{\mathrm{middle}}) / (s_{\mathrm{ref}} - s_{\mathrm{middle}})$, with its interval taken from the same resamples. Greedy decoding is repeatable on a serving node but not across all of them. Three nodes with the same GPUs served the runs. On two of them identical prompts gave identical answers: on MRCR, 14 runs on one node and a run on the other eight days later agree character for character on the 30 answers to the conversation that fits, and the last two ladder rungs agree on all 120 MRCR and 221 LongBench-v2 answers. The third node served every \recipe{} run and the BM25 runs away from the main window, and it answers the same prompts differently. The \recipe{} runs at the main windows repeat the final ladder rung with the same prompt for every question, yet flip the score of 4 of 120 MRCR answers and 6 of 221 LongBench-v2 answers. AA-LCR's long free-text answers vary far more. Where the recipe and, on another node, the recipe without the document floor built the same prompt, the grade differed on 9--19\% of questions, 14 in each direction, so differences of about 5 points between AA-LCR runs on different nodes are noise. Comparisons of the recipe with middle truncation and position cross nodes; this noise appears as paired disagreements, so the intervals include it. \review{Rerun the 17 runs from the third node (5 AA-LCR, 7 MRCR, 5 LongBench-v2) on one of the other two? Identical prompts should then give identical answers, and most of this paragraph could go. AA-LCR has no same-node repeat, so its repeatability is inferred from MRCR and LongBench-v2.}

\paragraph{Cost.} Table~\ref{tab:cost} reports input tokens and time per question. Selection embeds documents with Qwen3-Embedding-0.6B on one more L40S GPU. Each document set or conversation is embedded once, and the time is spread over the questions that share it. Selection time covers ranking and packing. Generation time is the time from sending the request to receiving the answer.

\paragraph{Selection, not structure, recovers accuracy.} A selected prompt differs from a truncated one in two ways: it keeps spans of the documents in order, under their headers and with omission markers, and it chooses those spans by the question. Position builds the same structure without the question, from the same chunks and with the same packing as BM25 and dense. Its gain over middle truncation is at most 6 points and never clear at any window: +6.0 [$-$4.6, +16.5] on AA-LCR, +0.0 [$-$2.5, +2.5] on MRCR and +1.8 [$-$1.8, +5.6] on LongBench-v2 at the main windows. Random chunks are no better than middle truncation, and neither marking the cut nor keeping the head changes the score. Every question-aware ranking, by contrast, beats middle truncation at the main window, except dense on LongBench-v2 (+5.0 [$-$1.6, +11.7]). Against position itself, BM25 and dense gain +21.7 [+13.3, +30.0] and +16.7 [+9.2, +24.2] on MRCR. On each of the other two benchmarks one of the two is clear: dense on AA-LCR (+10.0 [+2.0, +19.3]; BM25 +8.0 [$-$2.4, +18.4]) and BM25 on LongBench-v2 (+6.3 [+1.3, +11.6]; dense +3.2 [$-$3.0, +9.5]). None of the three covers every document: on AA-LCR at 64K, position leaves out at least one document for 62 of the 100 questions, BM25 for 64 and dense for 63. \review{Lead framing: on the direct contrasts with position, ``selection, not structure'' holds on MRCR, for BM25 on LongBench-v2 and for dense on AA-LCR; BM25 against position on AA-LCR is not clear at any window. Confirm before the Abstract and Introduction follow it.}

\paragraph{The \recipe{} beats position on AA-LCR and MRCR.} At the same window it gains +29.0 [+16.8, +41.5], +12.0 [+1.0, +23.8] and +13.0 [+5.0, +22.6] on AA-LCR at 32K, 64K and 80K. On MRCR it gains between +23.3 and +30.0 at every window, every interval above zero. On LongBench-v2 the margin is small and clear only at 128K (+2.7 [+0.4, +5.3]): at 64K the interval reaches zero (+5.4 [0.0, +10.7]), and at 32K it includes it (+3.2 [$-$4.2, +10.6]). The recipe differs from position in more than its ranking: its chunks are smaller, it fills the budget, and on AA-LCR its floor covers nearly every document, so these margins are not the effect of the question alone. \review{Control: position with the recipe's chunking, neighbours, fill packing and floor; see item 6 of the to-do list.} On AA-LCR, the recipe recovers 72\% [39, 104] of the accuracy middle truncation loses against full context at 64K, and 80\% and 95\% at 32K and 80K. At 32K it scores 56\% from 27\% of each prompt, against 21\% for middle truncation and 65\% for full context. LongBench-v2 leaves little to recover, since full context is only 5.9 points above middle truncation at 64K. There, BM25 and the recipe score 48.9\% and 48.0\%, no worse than full context (46.6\%) on less than half its input tokens.

\paragraph{BM25 gets most of the gain.} Dense ranking cannot be told apart from BM25 on any benchmark: BM25's difference from dense is $-$2.0 [$-$13.8, +7.9] on AA-LCR, +5.0 [$-$3.3, +13.3] on MRCR and +3.2 [$-$1.9, +8.3] on LongBench-v2. Fusing the two adds nothing over dense, and BM25 needs no embedding model. At the main window the recipe's four steps together add nothing clear to fusion either: +5.0 [$-$5.4, +16.1] on AA-LCR, +5.8 [$-$0.8, +12.5] on MRCR and $-$0.5 [$-$3.7, +2.7] on LongBench-v2. The recipe's margin over BM25 is clear on AA-LCR at 32K (+20.0 [+9.9, +32.3]) and 80K (+12.0 [+6.3, +18.3]) but not at 64K (+4.0 [$-$7.7, +17.2]). On MRCR it is clear at 32K and 128K (+10.8 at each, both intervals above zero) but not at 64K or 262K, and on LongBench-v2 it is absent. This margin mixes ranking with packing: at 32K, BM25's larger chunks leave 15\% of the budget unused on AA-LCR and 9\% on MRCR, and the recipe's fill packing leaves almost none. BM25 is not our main method because on AA-LCR it never separates from position, for instance +8.0 [$-$2.4, +18.4] at 64K. AA-LCR has no ladder, so we cannot say which of the recipe's steps makes the difference there. \review{Is this the right reason to lead with the recipe, or should BM25 share the headline? ``BM25 does not separate from position and the recipe does'' is not itself a clear difference at 64K (+4.0 [$-$7.7, +17.2]), and the margin over BM25 may come from chunking and fill packing, not fusion. \paragraph{Across windows.} Figure~\ref{fig:policies} shows the same order at every window. Position tracks middle truncation, and the recipe and BM25 lie above both on AA-LCR and MRCR. On LongBench-v2 every policy stays within 10 points at every window. There, the recipe's gain over middle truncation is +5.4 [$-$1.3, +12.4] at 32K and +3.2 [+0.4, +6.2] at 128K. At 128K middle truncation keeps 89\% of a prompt on average: 115 of the 221 prompts fit and every policy sends them whole, and the recipe's gain comes from the other 106, on which it gains 8 answers and loses 1.

\paragraph{Longer conversations.} At the 262K window, middle truncation falls from 60\% on the 133K conversation, which it sends whole, to 27\% and 10\% on the 533K and 1.06M ones, of which 48\% and 24\% fit (Figure~\ref{fig:mrcr-length}). BM25 scores 60\% on every conversation, and the recipe matches the oracle on the two longest, at 70\% and 63\%.

\paragraph{Ranking, not reading, limits the recipe on MRCR.} With the target turn hidden, exact match is 0\% in every row of Table~\ref{tab:visibility}. A policy's exact match is therefore the share of its prompts that show the target, times its exact match on those. Where the recipe shows the target, it answers as often as the oracle does on the same questions: 41 against 39 of 57 at 32K, 49 against 53 of 85 at 64K, and 68 against 63 of 107 at 128K. \review{These matched counts come from a one-off script over the predictions and needle spans; add them to \texttt{mrcr\_v2.visibility} so they are reproducible.} EM $\mid$ target is not comparable across rows, because a prompt that shows the target but hides other needles leaves the ordinal fewer candidates: middle truncation scores 82--86\% on the few targets it shows at 32K and 64K, where it almost never shows all four needles. What the recipe misses is the target itself, which it shows for 48\%, 71\%, 89\% and 100\% of questions from 32K to 262K. It therefore matches the oracle at 262K and at 128K, where the oracle leads by 2.5 [$-$4.2, +9.2]. It trails by 22.5 [+15.0, +30.8] at 64K and by 40.8 [+30.0, +51.7] at 32K. From 262K down to 32K, it recovers 100\%, 92\%, 53\% and 40\% of the oracle's gain over middle truncation. When the needles are guaranteed, less context helps: the oracle scores 75.0\% at 32K against 61.7\% at 262K (+13.3 [+4.2, +22.5]). On the 133K conversation, the only one with a full-context run, the oracle at 32K scores 70.0\% against full context's 60.0\% (+10.0 [$-$10.0, +30.0]). These 30 questions are too few to show that a focused prompt beats full context.

\paragraph{Cost.} On a GPU, selection costs little next to generation (Table~\ref{tab:cost}). BM25 adds 0.2\,s per question on AA-LCR and LongBench-v2 and 1.0\,s on MRCR. Counting embedding, the recipe adds 1.4\,s, 3.6\,s and 3.8\,s. On LongBench-v2, whose one-letter answers take 3.5\,s to generate, that roughly doubles the time per question. Full context sends 1.7 to 2.2 times as many input tokens as the 64K policies and is slower on both benchmarks that have a full-context run (9.7\,s against 8.2\,s on AA-LCR, 8.6\,s against 3.5\,s on LongBench-v2). On CPU, embedding took 91\,s per AA-LCR question and 22\,s per MRCR question, more than generation, which BM25 avoids entirely.

\section{Limitations}
All results come from one model, Qwen3.6-35B-A3B with thinking disabled, and from one run per condition; another model family or a reasoning mode may order the policies differently. The samples are small: 100 AA-LCR questions over 30 document sets, 120 MRCR questions over four conversations, whose intervals do not extend to other conversations, and 221 LongBench-v2 questions on which full context is only 5.9 points above middle truncation. We report many intervals without correcting for their number, and several that we call clear have a lower bound within a point of zero. One of the three serving nodes answers identical prompts differently, and every comparison of the \recipe{} with its baselines crosses that boundary.

The \recipe{} is a bundle we cannot take apart. No step is clear on the ladders, the bundle is not clearly better than plain fusion at the main window, and its margins over BM25 and position at smaller windows mix ranking with chunk size, fill packing and document coverage. \review{Rewrite these two sentences, and the node sentence above, if the two control runs and the same-node reruns happen.} Chunk size and the MRCR query were chosen on MRCR itself, and the ladders ran on the MRCR and LongBench-v2 questions we report; only AA-LCR is held out. MRCR is synthetic, and its query nearly repeats the needle requests, which favours lexical ranking. It is also the only benchmark on which we can measure visibility, because the other two do not release evidence locations. On AA-LCR and LongBench-v2 the overflow is imposed: the model's window holds every prompt, and we set a smaller budget. Only MRCR overflows the served window, and only its shortest conversation has a full-context reference. AA-LCR scores depend on an LLM grader, whose accuracy our check bounds only at 88\% or more, and on a 4,096-token answer cap that answers to truncated prompts reach more often than answers to full ones. Our LongBench-v2 protocol (a subset, our own system prompt and decoding constrained to one letter) is not the official one, so its scores are not comparable with published ones. Finally, the selection method is order-preserving retrieval and is not new; our contribution is the controlled comparison.
