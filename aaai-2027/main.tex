\begin{abstract}
\begin{notstarted}
When a long-context input is longer than the model's window, something must be removed. Benchmark harnesses usually cut out the middle of the prompt. We study this \emph{overflow policy} directly and treat retrieval as query-aware truncation: it re-renders the same prompt but keeps the chunks most similar to the question. On AA-LCR, MRCR v2 and LongBench-v2, served by one open-weight model at the same token budget, we compare it with naive truncation, structural and random controls, lexical retrieval and an oracle. The abstract will report how much of the accuracy lost to truncation it recovers, and how much of the oracle's gain.
\end{notstarted}
\end{abstract}

\section{Benchmarks}
We use three benchmarks, which differ in what an answer depends on: reasoning across several documents (AA-LCR), reproducing one passage of a long conversation (MRCR v2), and answering a four-option question about one long text (LongBench-v2). The served model reads up to 262K tokens, which holds every AA-LCR prompt and every LongBench-v2 prompt we keep. On these two benchmarks we therefore impose a 64K context window, so that every prompt overflows, and use the 262K run of the same prompt as the full-context reference. MRCR needs no imposed window: it uses the model's full 262K context window, which three of its four conversations exceed, and only the shortest, which fits, has a full-context reference. Table~\ref{tab:benchmarks} summarizes them.

\paragraph{AA-LCR.} Artificial Analysis Long Context Reasoning \review{cite AA-LCR} asks questions over sets of documents, mostly company documents (63 questions), followed by government consultations, industry reports, legal, marketing, academic and survey documents. A question comes with 2 to 24 documents (median 6). Answering can require finding the relevant documents, combining facts across them and computing a result. Answers are free text, and an LLM judge decides whether each matches the reference (see Experiments).

\paragraph{MRCR v2.} Multi-round coreference resolution (MRCR) v2 \review{cite MRCR v2} presents a long synthetic conversation in which the user repeatedly asks for a piece of writing with a given format, topic and style, such as ``write a poem about penguins in archaic style''. The same request is made four times, and each time the assistant writes a different response. We call these four exchanges the \emph{needles}. The final question asks the model to repeat one of them, for example the second, which we call the \emph{target}, and to start its answer with a given random string. The needles can be found in the conversation, so this is the only benchmark here on which we know where the answer is. We use the four-needle release and take its conversations of 133K, 267K, 533K and 1.06M tokens and 30 evenly spaced questions from each. An answer counts as correct only if it is the random string followed by the target response exactly; the benchmark's released scorer instead gives partial credit by string similarity.

\paragraph{LongBench-v2.} LongBench-v2 \review{cite LongBench-v2} has 503 four-choice questions over long texts. We keep the 221 whose full prompt overflows the 64K context window but fits the model's 262K; a longer prompt would have no full-context reference. They cover single-document QA (82 questions), multi-document QA (46), long in-context learning (44), dialogue history (20), structured data (17) and code repositories (12). The model answers with a single letter and no reasoning, so scoring is exact.

\section{Methodology}
A prompt holds fixed instructions, one or more source documents and a question. Its input budget is the context window minus the tokens reserved for the answer, counted on the fully rendered request with the served model's tokenizer and chat template. A prompt that fits is sent unchanged and an \emph{overflow policy} decides which source text to keep for a longer one. Every overflow policy keeps the instructions and the question whole, and all of them run in one pipeline that is otherwise the same, so two conditions on a benchmark differ only in the source text the model sees.

\subsection{Truncation Policies}
Truncation cuts the last message of the rendered request by token count. \emph{Middle truncation}, the protocol of LongBench and LongBench-v2 \review{cite LongBench, LongBench-v2}, keeps equal numbers of tokens from the start and the end of that message and silently drops the middle. \emph{Marked middle truncation} makes the same cut but inserts an omission marker, which tests whether knowing that text is missing helps the model. \emph{Head} keeps only the start of the documents, followed by the whole question.

\subsection{Selection Policies}
Selection rebuilds the request from a subset of its source text in three steps: chunking, ranking, and packing and rendering. Unless stated otherwise, every selection policy uses the same chunking and packing, so two of them differ only in their ranking.

\paragraph{Chunking.} Each document is split into overlapping chunks, measured with the embedding model's tokenizer. Unless stated otherwise, chunks are 7,500 tokens with 750 of overlap, and 3,500 with 350 on MRCR.

\paragraph{Ranking.} A ranking orders all chunks of a prompt, with no top-$k$ cut. Three rankings use the question: BM25 ($k_1 = 1.2$, $b = 0.75$, on lower-cased words) \review{cite BM25}; dense, by cosine similarity between Qwen3-Embedding-0.6B embeddings of each chunk and of an instruction-prefixed query \review{cite Qwen3-Embedding}; and fusion, by reciprocal-rank fusion ($k = 60$) of the two \review{cite RRF}. The query is the question on AA-LCR and the question with its four choices on LongBench-v2. On MRCR, it is the description of the requested item (its format, topic and style), because the prefix the answer must start with is random and the ordinal (``the second poem'') never appears in the conversation. The needle requests repeat this description almost word for word, which favors lexical matching. Two controls ignore the question. \emph{Position} ranks each chunk by how many chunks separate it from the start or the end of its document, whichever is nearer, taking the documents in order on ties. It is middle truncation applied to each document rather than to the whole prompt. \emph{Random} shuffles the chunks with a fixed seed per question. Because both controls share the chunks, packing and rendering of the three question-aware rankings, comparing them separates the effect of the prompt's structure from that of choosing text by the question.

\paragraph{Packing and rendering.} Chunks are added in rank order for as long as the re-rendered prompt fits the budget. Text that is kept, with overlapping chunks merged, goes back into the original prompt template in its original order with an omission marker wherever text was dropped inside a document, as in order-preserving retrieval \review{cite OP-RAG, DOS RAG}. On AA-LCR, a document with nothing kept is left out. By default, \emph{stop} packing stops at the first chunk that does not fit, so selection sends fewer tokens than truncation at the same budget: under 1\% fewer at MRCR's 262K window, 3--6\% at 64K and 7--15\% at 32K. \emph{Fill} packing, used by the \recipe, instead keeps adding lower-ranked chunks that still fit, then trims the best remaining chunk to the leftover budget.

\paragraph{The \recipe.} Our main method ranks by fusion and adds four steps to the default chunking and packing: (1) chunks of 1,024 tokens with 128 of overlap; (2) each ranked chunk widened by one neighbouring chunk on each side; (3) fill packing; and (4) a document floor, which places the best chunk of every document before any document's second chunk. We added the steps one at a time, as the rungs of an ablation ladder on MRCR and LongBench-v2 (see Experiments).

\paragraph{Oracle.} Because the needles can be found in the conversation, we can build an oracle from the \recipe. Chunks that overlap the target turn are offered first, then those overlapping the other needle turns, then the rest in the recipe's order. The information on the needle's location is only used to rank the chunks; chunk content, packing and prompt format are the recipe's. The oracle shows what the recipe's prompt achieves when ranking never misses the answer.

\paragraph{Provenance and visibility.} Each answer records the character ranges its prompt kept, and truncated prompts can be rebuilt exactly; Figure~\ref{fig:spans} draws these ranges for one AA-LCR prompt. On MRCR, we can tell whether each prompt contained the whole target turn and all needle turns. Exact match then splits into two factors (Table~\ref{tab:visibility}): the share of prompts that contain the target, and exact match on those prompts.

\section{Experiments}
\paragraph{Setup.} We serve Qwen3.6-35B-A3B \review{cite Qwen3.6}, an open-weight mixture-of-experts model with a 262K-token context window, with vLLM 0.19.1 \review{cite vLLM} on four NVIDIA L40S GPUs and send it one request at a time. Decoding is greedy with thinking disabled. AA-LCR uses its official prompt and MRCR v2 its released prompts. On LongBench-v2 a system prompt asks for a single letter, and decoding is constrained to A--D. The answer reserve is 4,096 tokens on AA-LCR and MRCR and 8 on LongBench-v2. Within a benchmark, every condition uses the same questions, prompt template, model and serving setup, and conditions are compared question by question. Unless stated otherwise, results are at each benchmark's context window in Table~\ref{tab:benchmarks}: 64K on AA-LCR and LongBench-v2, and the model's full 262K on MRCR.

\paragraph{Conditions.} A condition is one policy at one context window on one benchmark, with each random seed counted separately. Table~\ref{tab:conditions} lists all 93, grouped by what they test. Every window keeps the same answer reserve. AA-LCR stops at 80K because every prompt fits 128K, while at 80K none fits and middle truncation keeps 74\%. Only MRCR has an oracle, because only its evidence can be located. It also has no full-context condition: three of its four conversations exceed 262K, and on the shortest, middle truncation at 262K already sends every prompt whole. We fixed the \recipe{} on MRCR and LongBench-v2 at their context windows: an ablation ladder added its four steps to fusion one run at a time, and the final rung became the recipe before any run of it on AA-LCR or at another window. AA-LCR, the only benchmark whose questions come with several separate documents, is therefore held out: no setting of the recipe was chosen on its scores. The document floor has no effect on a single document, so it could not be tested on MRCR or LongBench-v2. On AA-LCR, after the recipe was fixed, we ran it without the floor at every window, and the ladder's first two rungs at 64K, which complete the ladder there. Two dense variants on MRCR give it the two settings that the other benchmarks use by default: one queries with the full question, the other uses 7,500-token chunks. Two controls were designed after the recipe's results were known. Each takes the recipe's four steps and changes only the ranking: the \emph{position recipe} ranks by position, and the \emph{BM25 recipe} by BM25 alone. MRCR and LongBench-v2 have no position recipe: each of their prompts holds one text, on which position keeps the head and the tail, in effect marked middle truncation. Window sweeps cover only the policies that Figure~\ref{fig:policies} follows and, on AA-LCR, the recipe without the floor; full context runs at 262K, and every other condition at the benchmark's context window.

\paragraph{Grading.} MRCR and LongBench-v2 are scored deterministically against their reference answers. AA-LCR is graded by the benchmark's equality checker, an LLM judge (GPT-5.6 Luna at medium reasoning effort), with the official grader prompt and the benchmark's rules for equivalent answers added \review{Cite the AA-LCR methodology page for the checker model}. To check Luna, we also graded every answer with the served model. We then labeled by hand every answer the two graders disagree on, plus a random sample of those they agree on, without seeing either grade. We estimate Luna's accuracy at 95.3\% (95\% interval [84.9, 99.1]), and its errors change no run's accuracy by more than two points (Table~\ref{tab:grader}, in the appendix). AA-LCR's prompts do not ask for an answer format, and with thinking disabled the model often works through the problem in its answer; the judge grades the value the answer finally commits to. Across all AA-LCR runs, 4.6\% of answers reach the 4,096-token cap, and Luna marks 136 of these 144 as incorrect.

\paragraph{Statistics.} Each condition runs once. We report paired differences from middle truncation at the same window, with 95\% percentile intervals from 10,000 bootstrap resamples drawn with a fixed seed. Questions that share a source are resampled together (the 30 document sets of AA-LCR and the 194 texts of LongBench-v2). MRCR has only four conversations, so we resample questions within each conversation, and its intervals hold for these four conversations only. Two comparisons answer the paper's central questions: the \recipe{} against middle truncation, and against position, which keeps the same structure without the question. We test both at every window on every benchmark, 20 comparisons in all, with a two-sided paired randomization test that swaps the two policies' outcomes in the same groups as the bootstrap (100,000 swaps), and correct the 20 $p$-values together with Holm's method (Table~\ref{tab:primary}, in the appendix). We call a difference significant only when its corrected $p$-value is below 0.05. Every other comparison is exploratory, and we report its interval without correction. Greedy decoding is repeatable in our setup: the two serving nodes that ran every reported run gave identical answers to identical prompts (see the appendix).

Table~\ref{tab:main} compares every policy at each benchmark's context window, and Figure~\ref{fig:policies} follows the main policies across windows. Differences are in points, against middle truncation at the same window unless stated otherwise.

\paragraph{Selection recovers most of what truncation loses.} On AA-LCR, the \recipe{} recovers 84 to 96\% of the accuracy that middle truncation loses against full context, at every window. At 64K it scores 64\%, against 40\% for middle truncation and 65\% for full context, and at 32K it still scores 58\% from about a quarter of each prompt. LongBench-v2 leaves little to recover, since full context is only 5.9 points above middle truncation at 64K. There, BM25 and the recipe match full context on less than half its input tokens, and at 128K, where half the prompts fit and every policy sends them whole, neither gains more than 2 points over middle truncation. On MRCR at the 262K window, middle truncation falls from 60\% on the conversation that fits to 10\% on the longest, while the recipe matches the oracle on every conversation (Figure~\ref{fig:mrcr-length}). The recipe's gain over middle truncation is significant at every window on AA-LCR and MRCR, and at none on LongBench-v2 (Table~\ref{tab:primary}).

\paragraph{Structure alone recovers little.} A selected prompt keeps spans of the documents in order, under their headers and with omission markers, and chooses those spans by the question. Position and random chunks build the same structure without the question. Neither does better than middle truncation: position stays within 6 points of it at every window, and no interval for position or random chunks excludes zero; marking the cut or keeping only the head changes nothing (Table~\ref{tab:main}). The one exception is the position recipe on AA-LCR at 32K, which gains 21 points (95\% interval [+8.4, +32.7]) without using the question: its small chunks, fill packing and document floor keep text from nearly every document, where position leaves out a document for 86 of the 100 questions. Part of what the \recipe{} recovers on AA-LCR at small windows therefore comes from structure, not from the question.

\paragraph{Ranking by the question adds to structure.} At each benchmark's context window, every question-aware ranking scores above middle truncation, with an interval that excludes zero for all but dense on LongBench-v2 (Table~\ref{tab:main}). The primary test is the \recipe{} against position, which builds the same structure without the question. The recipe is significantly better on MRCR at every window, by 23 to 30 points, and on AA-LCR at 32K and 64K, by 31 and 18 points, but not at 80K or on LongBench-v2 at any window (Table~\ref{tab:primary}). The position recipe, which differs from the recipe only in its ranking, agrees on AA-LCR: the recipe leads it by 16 points at 32K and by 12 at 64K ([+2.9, +23.0]), and by 9 at 80K, where the interval includes zero.

\paragraph{The steps help, and no ranking wins everywhere.} With the default chunks, BM25, dense and fusion cannot be told apart at any benchmark's context window. Given to BM25, the \recipe's four steps add 10 to 21 points on MRCR at every window below 262K and 12 to 13 points on AA-LCR at 32K and 80K, but change it by $-$2.5 to +2.3 points, with intervals that include zero, on AA-LCR at 64K, on MRCR at 262K and on LongBench-v2 at every window. Part of this gain is packing: at 32K, BM25's larger chunks leave 15\% of the budget unused on AA-LCR and 9\% on MRCR, while fill packing uses nearly all of it. Added one at a time on the ladders (Table~\ref{tab:ladder}, in the appendix), only one step has an interval that excludes zero: one neighbouring chunk on each side, worth +11.0 [+3.5, +18.1] points on AA-LCR, +5.0 [$-$1.7, +11.7] on MRCR and $-$3.6 [$-$7.7, +0.4] on LongBench-v2. On AA-LCR, where the ladder ran after the recipe was fixed, the rung that ends with this step scores 67\%, above the recipe's 64\%, and dropping the document floor changes the recipe by at most 2 points at any window, with intervals that include zero. The recipe stayed as fixed. MRCR's query and chunk size matter too: with the full question as the query, or with 7,500-token chunks, dense exact match falls by 9 points ([$-$15.0, $-$4.2]) and by 10 ([$-$17.5, $-$2.5]). With the steps equal, the better ranking depends on the benchmark. Fusion leads BM25 on AA-LCR at 64K (+11.0 [+5.0, +17.8]), and BM25 leads fusion on MRCR at 64K (+11.7 [+2.5, +20.8]), as expected of a query that nearly repeats the needle requests. BM25 also leads on LongBench-v2 at every window, by 0.9 to 2.7 points; no other interval excludes zero. We keep the \recipe{} as our main method because it was fixed before these runs, with AA-LCR held out; the BM25 recipe is the alternative that needs no embedding model.

\paragraph{On MRCR, ranking limits the recipe, not reading.} With the target turn hidden, exact match is 0\% in every row of Table~\ref{tab:visibility}, so a policy's exact match is the share of its prompts that show the target times its exact match on those. Where the recipe shows the target, it answers about as often as the oracle does on the same questions, within five answers at each window. \review{These matched counts come from a one-off script over the predictions and needle spans; add them to \texttt{mrcr\_v2.visibility} so they are reproducible.} What it misses is the target itself: at 32K it shows the target for 48\% of questions and recovers 43\% of the oracle's gain over middle truncation, and both rise to 100\% at 262K. The BM25 recipe finds the target more often and recovers more at every window below 262K. When the needles are guaranteed, less context helps: the oracle scores 75.0\% at 32K against 61.7\% at 262K (+13.3 [+4.2, +22.5]). On the one conversation with a full-context run, though, 30 questions are too few to show that a focused prompt beats the full one.

\paragraph{Cost.} On a GPU, selection costs little next to generation: BM25 adds 0.2 to 1.0\,s per question and the \recipe{}, counting embedding, 1.4 to 3.7\,s, while full context sends 1.7 to 2.2 times as many input tokens as the 64K policies (Table~\ref{tab:cost}, in the appendix).

\section{Limitations}
All results come from one model, Qwen3.6-35B-A3B with thinking disabled, and from one run per condition; another model family or a reasoning mode may order the policies differently. The samples are small: 100 AA-LCR questions over 30 document sets, 120 MRCR questions over four conversations, whose intervals do not extend to other conversations, and 221 LongBench-v2 questions on which full context is only 5.9 points above middle truncation. Only the 20 primary comparisons are corrected for their number; the many other intervals we report are exploratory, and several that exclude zero do so by less than a point.

The recipe's four steps are hard to take apart: on the ladders only the neighbouring chunks on AA-LCR have an interval that excludes zero, one of twelve uncorrected step comparisons, and the same step costs 3.6 points on LongBench-v2; the controls change the recipe's ranking, not its steps. The controls were designed after the recipe's results were known, and the position recipe ran on AA-LCR only. They do not agree on a ranking: fusion leads on AA-LCR and BM25 on MRCR, each with an interval that excludes zero at one window, and BM25 leads on LongBench-v2 with intervals that include zero. Chunk size and the MRCR query were chosen on MRCR itself, and the ladders ran on the MRCR and LongBench-v2 questions we report; only AA-LCR is held out. MRCR is synthetic, and its query nearly repeats the needle requests, which favors lexical ranking. It is also the only benchmark on which we can measure visibility, because the other two do not release evidence locations. On AA-LCR and LongBench-v2 the overflow is imposed: the model's context window holds every prompt, and we impose a smaller one. Only MRCR overflows the model's context window, and only its shortest conversation has a full-context reference. AA-LCR scores depend on an LLM grader, whose accuracy we estimate at 95.3\% but can bound only at 84.9\% or more, and whose grades vary slightly between calls. They also depend on a 4,096-token answer cap, which answers to truncated prompts reach more often than answers to full ones. Our LongBench-v2 protocol (a subset, our own system prompt and decoding constrained to one letter) is not the official one, so its scores are not comparable with published ones. Finally, the selection method is order-preserving retrieval and is not new; our contribution is the controlled comparison.

\section{Appendix: Serving Nodes}
Every reported run was served by one of two nodes with the same GPUs. A third node, which first served the \recipe's runs and the BM25 runs at the windows other than each benchmark's context window, answers identical prompts differently from the other two. We reran those runs on one of the two nodes, as decided before the reruns and whatever their results, and report only the reruns. On the two nodes, greedy decoding is repeatable: the \recipe{} at each benchmark's context window builds the same prompts as the final ladder rung and repeats its answers to all 120 MRCR questions on the other node and to all 221 LongBench-v2 questions thirteen days later. On AA-LCR, the recipe with and without the document floor give the same answer to all 191 questions for which they built the same prompt.

\section{Appendix: Cost}
Table~\ref{tab:cost} reports input tokens and time per question at each benchmark's context window. Selection embeds documents with Qwen3-Embedding-0.6B on one more L40S GPU. Each document set or conversation is embedded once, and the time is spread over the questions that share it. Selection time covers ranking and packing, and generation time runs from sending the request to receiving the answer. BM25 adds 0.2 to 1.0\,s per question and the \recipe{}, counting embedding, 1.4 to 3.7\,s; only on LongBench-v2, whose one-letter answers take 3.5\,s to generate, does that roughly double the time per question. Full context sends 1.7 to 2.2 times as many input tokens as the 64K policies and takes longer on both benchmarks that have it. On CPU, embedding took 91\,s per AA-LCR question and 22\,s per MRCR question, more than generation; BM25 and the BM25 recipe embed nothing.
